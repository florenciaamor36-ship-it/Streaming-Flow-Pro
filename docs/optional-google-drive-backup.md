# Optional personal Google Drive sync (Android)

This branch adds an opt-in, explicit-action-only Drive sync through the Google Drive v3 `appDataFolder` API. Room remains the offline source of truth. No sync runs on login, startup, or in background; the user must enable the feature and tap Sync / Create backup / Restore.

## Wire format v1

The app writes one `stream-flow-pro-data-v1.json` file in the signed-in user's `appDataFolder`, using the web branch filename and a compatible envelope superset: `schemaVersion` (1), `app` (`stream-flow-pro`), `writerId`, `ownerEmail`, opaque app `revision`, `parentRevision`, ISO-8601 `updatedAt`, SHA-256 `contentSha256`, and `data` with `accounts`, `sales`, and `clients` arrays. Rows have stable IDs; arrays are sorted by ID before hashing and writing. A checksum mismatch, duplicate IDs, unknown schema version, account mismatch, multiple files, or stale Drive ETag prevents changes. Drive file updates use `If-Match`; a 412 is surfaced as a conflict. There is one current snapshot rather than a revision history.

The data mapping intentionally excludes account passwords, profile passwords/PINs, service login email addresses, supplier phone numbers, and freeform notes. Those are preserved on the same device for IDs already present during a restore; they are never restored from Drive. It includes sales amounts, platform/profile/client names and client contact fields; this remains commercially and personally sensitive information. **`appDataFolder` is not encryption**: this implementation does not provide client-side encryption. Do not enable it unless you accept that included data is stored in Google's Drive under that account.

## Identity and consent

Authorization is requested only after the user taps an action, via Google Identity `AuthorizationClient`, requesting only `https://www.googleapis.com/auth/drive.appdata`. The authorization result's Google account email must match the app's verified Firebase email. Guest/local-fallback app sessions are rejected. Access tokens are passed in memory to the Drive transport only and are not logged or persisted. Turning the feature off prevents sync calls; no WorkManager/background task is registered.

The Cloud project must enable Google Drive API and configure an Android OAuth client for application id `com.aistudio.controlstreaming.sales` plus the actual app signing certificate SHA-1. `GOOGLE_DRIVE_CLIENT_ID` is a build-time Gradle property (`-PGOOGLE_DRIVE_CLIENT_ID=...`) / Gradle property, not a client secret; without it the action fails closed. No OAuth client secret or assistant account is present in the app. Debug and Play/release signing fingerprints differ and each needs owner configuration. The configured client identifier is a provisioned-client guard; Android's installed-app OAuth binding itself is resolved by package + signing certificate in Google Cloud.

## Conflict and restore safety

Initial upload requires the separate **Create backup** button and a dialog showing local row counts. Initial restore requires a separate confirmation and only imports when Room has no rows. Normal sync fast-forwards remote only if local still matches its base; it uploads local only if Drive still matches the base; concurrent/divergent changes are blocked rather than silently overwritten. Drive/Room work runs off main thread, and import is transactional and scoped to the verified Firebase user ID. A write also carries a Drive ETag precondition. The user must compare/export data manually to resolve a conflict; there is no automatic merge or tombstone model yet. Emptying all local tables does not cause an implicit destructive restore/upload.

## Validation and limitations

Unit tests cover serialization/checksum/version metadata, policy decisions, fake-transport create/update, sensitive-field omission, identity mismatch, and conflict blocking. Fake transport tests do not prove the owner's OAuth configuration, real Google account authorization, or actual Drive API requests. Real API testing requires the app owner's Cloud OAuth setup and a verified Firebase session whose Google address matches exactly. The Android payload uses the same file name, app identity, and versioned envelope family as web, but the web branch currently has no `ownerEmail`/app revision contract, strips the `customers` directory, and uses different account/sale field shapes. Android maps its clients to `data.clients`; until the web schema and its privacy filtering are explicitly updated to the same field contract, cross-platform row-level interoperability is not claimed. No Firebase/Firestore code, production database, rules/config, release signing, APK publishing, deployment, billing, or `main` branch was changed.
